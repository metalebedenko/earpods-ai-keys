# EarPods AI Keys — native app specification

Status: approved after two independent review iterations (97.5/100; see reviews/menu-bar-spec-review.md). Implementation approved by the author on 2026-10-10; additional input/control permission prompts are acceptable. Publication and paid signing services are not authorized.

## Goal and scope

Replace routine terminal use with a native menu-bar app: drag into Applications, launch, enable the remote, configure its three buttons, optionally launch at login, and remove it from the menu. Reconnect must restore an enabled profile without a repeating timer.

Use Swift/AppKit, IOKit, CoreGraphics and ServiceManagement on macOS 13+. No runtime dependencies, global keyboard event tap, reserved F-key bridge, driver, virtual-HID entitlement, periodic device polling, network access or telemetry. This version supports one matching USB-C EarPods Consumer Control service (VID 1452, PID 4363, page 12, usage 1), one action per physical press, and modifiers Command/Control/Option/Shift. Multiple matching services are a visible conflict. Macros, app-specific profiles, double-click/hold gestures and other headset models are outside this version.

## User contract

- The app has no Dock icon or startup window. Its menu shows the current mode, device availability and errors; it offers Enable/Disable, Configure buttons, Launch at login, Disable and quit, and Uninstall.
- First launch starts disabled with the default profile: center = native Dictation (Consumer VoiceCommand CF), minus = Backspace, plus = Enter. Login registration starts off. Later launches restore the saved enabled intent.
- Settings show three rows. An action is native Dictation or a single key with zero or more supported modifiers. Recording uses a focused local AppKit responder, never a global keyboard listener. A Reset assignments button restores the default profile; disabling/uninstalling restores owned rules to stock media behavior.
- Enabled without EarPods means Waiting for EarPods. Device arrival triggers reconciliation; removal stops input handling and changes the status. Startup also enumerates already-connected devices. No process-existence check is used as evidence that remapping is active.
- Active means exact HID rule readback succeeded and every required chord-input/posting capability is ready. Missing permissions, conflicts and failures show actionable messages rather than a checked-but-inoperative mode. The requested mode is retained while waiting; disabling cancels pending work before clearing rules.
- Preserve the existing Siri/Dictation preferences. Native Dictation's Siri-off prerequisite remains documented; CF is not a universal Dictation API.

## Backend and ownership

1. Observe matching IORegistry device arrivals/removals with IOKit notifications. Process initial iterators to enumerate and arm callbacks. All controller mutations run serially on the main actor; generation tokens cancel old arrivals and permission callbacks.
2. Preserve native single-key/VoiceCommand mapping through hidutil. For a chord action, the candidate mapping sends that source to Keyboard NoEvent (usage 0); a nonexclusive IOHIDDevice callback reads that button's original input and posts the configured key-down/key-up with CoreGraphics modifiers. On the first physical down, emit the complete synthetic down/up pair synchronously without an await or cancellation point; physical release only rearms that source. Subscribe only to the matched EarPods and emit only configured chord actions, once per press/release cycle. Do not synthesize separate modifier-down events. If posting capability is lost during the pair, attempt the matching key-up, stop input and show an error; never infer successful delivery from CGEventPost's void return.
3. This hybrid route is a hardware gate, not an API-proven result: original raw usages must remain visible, NoEvent must suppress stock media actions, and center Dictation must continue. Never silently substitute whole-device seizure, private media-event APIs, virtual-HID entitlements or a global keyboard tap. If the gate fails, preserve the working setup and report that chords require a revised design; the app's default mode remains usable.
4. For chord profiles, preflight listening/posting access and open the required nonexclusive device input before installing the chord-suppression rule. Ask only for missing capabilities on explicit user action. Permission checks never grant access themselves. On read/post failure, stop chord input, clear an exactly owned rule if possible and show the error.
5. Read/normalize one exact mapping. Blank output means absent; null/empty arrays mean no rule; malformed, multiple-service and unknown nonempty mappings are refused. Capture errors/nonzero exits without broadening matches. Only configured sources CD/EA/E9 and validated native usage destinations are permitted.
   Native command execution also has a bounded deadline and output limit. Timeout, output overflow and unreadable replies fail closed; partial output must not be parsed as device absence. Production executable paths are fixed and no shell is involved.
6. Persist an atomic ownership receipt before a mapping write. It records both last verified and pending intended exact pair sets, so a crash between write and readback is recoverable. Clear only an exact receipt-owned rule; preserve all foreign rules. Profile editing while enabled serially reconciles the full set with rollback to the last verified profile on failure. A failed update never reports the requested profile active.
7. An arrival may schedule at most five readiness attempts (immediate, 0.1, 0.3, 1 and 2 seconds); cancellation or removal ends them. No retries for malformed/foreign state or denied permissions, and no indefinite timer. Opening the menu or choosing Enable may request a fresh read.

## Login, migration and removal

- Use SMAppService.mainApp for optional login startup, reflect its actual registration/approval status and handle errors. Do not register at first launch without the user's toggle.
- Detect earlier personal/public login jobs. A public CLI installation is owned only after its marker and fingerprints validate; personal installations are not automatically adopted. While an old job exists, refuse activation and offer a reviewed migration/cleanup path. Migration must preserve an exact backup and stop the old owner before the new one writes. Initial implementation may use the existing verified CLI uninstall for owned public installations; no generic directory deletion or silent takeover.
- Uninstall has one clear confirmation naming the app-owned changes and app path. Cancel input/arrival work, disable the saved mode, clear only an exactly owned rule, unregister the app's login item, remove only its preferences/support files, and quit. Unrelated Siri/Dictation preferences and foreign files/mappings remain untouched; report preserved conflicts separately. If clearing/verifying an owned mapping or unregistering login fails, retain the receipt, settings and app, do not schedule self-Trash, show the remaining state and offer Retry. A deliberately preserved foreign rule is not a failed owned cleanup. An absent device has no live owned rule to clear; retain the disabled intent until normal removal completes.
- Move the verified app bundle to Trash after the main process exits, using a short-lived cleanup helper if required. Validate bundle identity/canonical path and use native file APIs, no interpolated shell commands, recursive wildcard cleanup or emptying Trash. The helper must remove its own temporary file when done. If Trash/permissions/in-use handling fails, show the precise remaining app path and Finder fallback. Never call partial removal complete.
- The development bundle uses ad-hoc signing and is not advertised as a notarized public release. Gatekeeper may require user approval when transferring it. Developer ID/notarization and paid-account access are a later explicit release step.

## Implementation order and validation

1. Review this specification; build original-code backend probes and pure model/parser tests without changing the working Mac configuration.
2. Compile the hybrid route. On the author-approved hardware test, capture the exact working map, test one chord button and restore it on normal exit/interruption. Validate raw input, suppression, no double action, center Dictation and modifier release. The author will connect EarPods to the first Mac; permission prompts require his interaction.
3. Implement the state controller, receipts, notification/input adapters and tests. Test absence, arrival, removal during apply, pending retry cancellation, denied/revoked permissions, multiple devices, foreign mapping, malformed output, crash receipt recovery, edited profile rollback and release/duplicate input. Test disable/removal/profile change between synthetic down and up with a fake emitter and confirm the release attempt; repeat denial-after-down without claiming successful delivery.
4. Implement menu/settings/recording UI and login/removal adapters. Test preference validation, native permission/login status, migration refusal and isolated owned cleanup/partial failures. In particular, failed owned-map readback or failed login unregistration must retain the recovery receipt/app and inhibit self-Trash. Provide a deterministic render mode for visual verification without hardware writes, login registration or input capture.
5. Build an Applications bundle and a transferable development ZIP. Keep the shell CLI intact as a recovery/reference route. Update setup/current-state material; do not publish or commit.
6. Run meaningful Swift tests, shell regressions if shared behavior changed, compile checks and visual inspection. Then test the actual app on the first Mac with the user's interaction and later on the second Mac: default profile, chord profile, off/on, reconnect, boot with/without headset, quitting, defaults and complete removal. Record software tests separately from physical results.

## Acceptance and open gates

A development candidate is ready to hand over when the app builds, isolated checks pass, menu/settings render correctly, and every requested operation has an implemented path with honest failure status. It is not a completed hardware acceptance or public release.

Functional acceptance requires default Dictation/Backspace/Enter and one configured Command chord on both Macs, no simultaneous media action, normal media controls after Disable/Quit, successful reconnect after a disconnected login with mode enabled, and uninstall with no owned login job/process/settings left. Timing/resources must be observed rather than promised; zero periodic polling is required.

Open gates: the hybrid chord route on real EarPods, actual permission behavior and revocation, migration of the first Mac's personal installation, and self-Trash from writable Applications. Public signing/notarization credentials are not yet available or requested. A gate failure must change the implementation/release status, not disappear from the report.
